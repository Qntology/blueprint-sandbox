## 배경: 현장에서 납득되는 이슈인가

### 💡 질문 1: 이 이슈들이 발전소 현장에서 납득이 되는 이슈야? 그냥 무작위야?

**결론부터 말씀드리면, 무작위(Random)가 아니라 실제 한국 발전소(5대 발전사·한수원)의 ‘고장정지 분석보고서’와 ‘비정상 운전절차서(AOP)’에서 가장 빈번하게 발생하는 4대 대표 사고 유형(Archetype)을 정확히 발췌한 것입니다.**

다만 이전까지는 설명을 위해 4가지 예시(`P1`~`P4`)로 압축해 보여드렸다면, 실제 발전소 현장 엔지니어들이 100% 납득하려면 이슈의 성격을 다음 3가지 차원(단일 이슈 / 절차 이슈 / 다중·복합 이슈)으로 명확히 분류해서 다루어야 합니다.

| 이슈 분류 | 발전소 현장에서 왜 납득되는가? (현업 리얼리티) | 기존 `zoro-gravity` 코드와의 1:1 대응 |
| --- | --- | --- |
| **① 단일 이슈**<br>*(Single Issue)* | **현장 빈도 70%**: 설비 자체가 터진 게 아니라, 고온·진동 환경 때문에 **센서 1개가 영점이 틀어지거나(Drift), 단위 부품 1개(베어링·차단기)만 국소적으로 이상**이 생긴 경우입니다. 이때 발전소를 세우면 수억 원 손해이므로 ‘단일 계측기 오류’로 즉시 걸러내야 합니다. | `Gate 1` (신호 무결성) & `Gate 2` (`check_rent` 대응 — 인쇄 원장 vs 단일 입력 대조) |
| **② 절차 이슈**<br>*(Procedural Issue)* | **현장 빈도 20% (인적 오류 1위)**: 설비 고장이 아니라 **사람이 일하는 절차(SOP/MOC/LOTO)가 어긋난 이슈**입니다. 작업허가서 서명 누락, 승인 안 된 Red-line 도면 임의 적용, 상류 압력을 안 빼고 하류 밸브부터 여는 **‘조작 순서(Interlock) 위반’**이 여기에 해당합니다. | `OutcomeClass::Procedural` (`G1SignInvalidRetry`, `IssueSupplement`, `ForcePassToGate2` 차단) |
| **③ 복합·다중 이슈**<br>*(Multi-Part / Cascading Issue)* | **현장 빈도 10% (가장 치명적)**: **물리적 연쇄 파급**(103동 급수밸브 고착 ➔ 101동 보일러 과열 ➔ 102동 터빈 압력 흔들림)에 **센서 노이즈나 정비 작업까지 겹친 상황**입니다. 알람이 동시에 20개가 울리므로 단순 규칙 하나로는 못 잡고 마인드맵(`graph.rs`) + `judge_by_criteria` 분할 질문이 필수입니다. | `Gate 3` (`relations`, `SUBSIDY_CRITERIA` / `PERMIT_CRITERIA` 다중 기준 분할 질문) |

## Part 8-6. 발전소 단일·절차·복합(다중) 이슈 분류 및 다층 의사결정 개선 기획 (`docs/powerplant-multi-issue-plan.md`)

단순히 알람 하나에 원인 하나를 매칭하는 1차원 판정을 넘어, 발전소 현장에서 발생하는 문제를 ① 단일 이슈(Single Component/Sensor), ② 절차 이슈(Procedural/Human/MOC), ③ 복합·다중 계통 이슈(Multi-Part/Cascading)로 엄격히 구분하고, 각 이슈 성격에 맞춰 `Gate 1~3`와 `Zoro-1`(`judge_by_criteria`)이 서로 다른 의사결정 트리로 대응하도록 개선하는 기획입니다.

### 1. 발전소 3대 이슈 분류 체계 및 현장 납득 시나리오 매트릭스

무작위 난수 생성이 아니라, 물리적 인과관계와 발전소 표준 운영절차(SOP/AOP/LOTO/MOC)에 기반한 9가지 현장 납득형 이슈 카탈로그입니다.

| 대분류 | 세부 이슈 유형 | 실제 발전소 현장 상황 (왜 납득되는가?) | 담당 Gate 및 판정 클래스 (`OutcomeClass`) |
| --- | --- | --- | --- |
| 유형 A.<br>단일 이슈<br>*(Single Issue)* | **A-1. 단일 계측기 드리프트/단선** | 터빈 주증기 압력 전송기 A만 $14.2\text{ MPa}$로 급락하고 보조 B·C 및 현장 아날로그 게이지는 $26.0\text{ MPa}$ 정상 유지 (센서 1개 단독 고장) | • **Gate 1~2** 단독 종결<br>• `Procedural` (계측팀 정비 배정, 트립 보류) |
|  | **A-2. 단일 설비 국소 열화** | 상·하류 유량과 압력은 모두 정상인데 `102동 고압터빈` 1번 베어링 메탈 온도만 윤활유 스트레이너 미세 막힘으로 단독 상승 | • **Gate 3** (`close_path == None`)<br>• `Adverse` 또는 `Favorable` (예비 윤활유 냉각기 전환) |
|  | **A-3. 스캔 문서/명판 단일 오독** | 현장 운전원이 스캔한 점검표에서 KKS 코드 1글자(`1`➔`I`) 오독 또는 허용 범위 내 미세 편차 | • **`extract.rs` & `Lattice**` 자동 교정 후 정상 통과 |
| 유형 B.<br>절차 이슈<br>*(Procedural Issue)* | **B-1. 안전작업허가(LOTO)·서명 불비** | 현장 밸브 수동 조작 전 필수인 작업책임자 전자서명 누락(획수·면적 미달) 또는 안전 점검표 미스캔 상태에서 조작 시도 | • **Gate 1** (`G1SignInvalidRetry` / `Hold`)<br>• `Procedural` (현장 단말 재서명·보완 요구) |
|  | **B-2. 변경관리(MOC) 절차 위반** | 부품 교체 후 정식 `moc_ledger` 승인 번호 없이 현장 Red-line 도면에 볼펜으로만 임계치를 높여 적어 제출 (`check_manual_amount` 대응) | • **Gate 2** (`G2RejectContradictionLock`)<br>• 무증빙 임계치 상향 즉시 차단 |
|  | **B-3. 조치 순서(Interlock) 역순 위반** | 상류(`Depth -1`) 펌프 압력을 낮추거나 우회 밸브를 열지 않은 채 고착된 주 조절밸브(`Depth 0`)부터 강제 개방/확정 시도 (`ForcePassToGate2` 대응) | • **Gate 1~3 가드레일** (`CaseOutcome::Blocked`)<br>• 선행 절차 완료 전까지 확정 원천 잠금 |

|  | **C-2. 다중 원인 동시 중첩 (Compound)** | `103동 급수밸브` 개도 불량(설비 이슈)이 발생한 상태에서, 하류 `101동 온도센서`까지 노이즈(계측 이슈)가 껴서 위험도가 부풀려진 상황 | • **Gate 2 + Gate 3 복합 심사**<br>• `judge_by_criteria`로 센서 오류와 실제 유량 부족을 분리 판정 |
|  | **C-3. 설비 고장 + 절차 위반 결합** | 실제 고압터빈 베어링 진동이 트립 한계($200\ \mu\text{m}$)를 넘었는데(`Adverse`), 교대감독이 입증 자료나 파트장 공동결재 없이 단독으로 ‘정상 운전 유지’를 누름 | • **Gate 3 (`officer_approve`)**<br>• `G3InterceptRubberStamp` 발동하여 고위험 무입증 승인 즉시 차단 |

### 2. 단일 · 절차 · 복합 이슈를 가르는 파이프라인 의사결정 구조화

현재 `core/src/state_machine/gate3_substantive.rs`와 `verdict.rs`를 보면, 민원 심사에 `PERMIT_CRITERIA`(`["위반건축물 여부", "건축물 용도 적합 여부", "필증 유효 여부"]`)와 `SUBSIDY_CRITERIA`(`["거래처 특수관계 여부", "입찰 회피 분할 결제 여부"]`)처럼 **다중 이슈를 쪼개어 묻는 구조**가 이미 완벽히 구현되어 있습니다.

### 3. 이슈 유형별 상세 로직 설계 (`core` 모듈 매핑)

#### 3.1 절차 이슈(Procedural Issue) 전담 가드레일 설계 (`gate1_formal.rs` & `intake.rs`)

실제 발전소 사고의 상당수는 "고장 난 설비를 고치려다 절차를 어겨서 더 큰 사고를 내는 것"입니다. 기존 코드의 불변식 2(*"절차 처분은 자동 확정하지 않습니다"*)와 불변식 6·7(*"고위험 무입증 승인 및 누락 서류 강제 진입 차단"*)을 그대로 발전소 절차 검증에 매핑합니다.

1. **선행 인터록 절차 체크리스트 (`PlantChecklist` — 기존 `Checklist` 확장)**:

* 단일 설비 조작이든 복합 계통 조작이든, 해당 설비의 `interlock_procedures`(Step 1 ➔ Step 2 ➔ Step 3)가 순서대로 완료되지 않으면 `ChecklistIncomplete(missing)` 에러를 반환하여 다음 단계 진입을 막습니다.

2. **무증빙 기준치 변경 차단 (`check_manual_spec` — 기존 `check_manual_amount` 대응)**:

* 운전원이나 정비팀이 `moc_ledger` 승인 번호나 스캔 증빙 없이 임의로 경보 임계치를 상향 조정하려 하면 즉시 `DeskError::Blocked`로 차단하고 감사 로그에 기록합니다.

3. **고위험 경보 무시(Rubber-Stamp) 차단 (`officer_approve` 그대로 활용)**:

* `G3ViolationHighRisk`(트립 임계치 돌파) 상태에서 교대감독이 정상 운전 유지(`ApproveHighRisk`)를 누르려면 반드시 다음 3가지 입증(`Justification`) 중 하나가 있어야만 통과됩니다:

* `ProveFalsePositive { evidence_scans }`: 현장 게이지 정상 스캔본 1장 이상 첨부 (계측기 오작동 입증)

* `ApplyLawException { team_lead_cosign: true, rule_ref }`: 발전부장/파트장 공동 결재 + 비상운전절차서(AOP) 조항 번호 기입 (`special_audit_flag = true` 자동 부착)

#### 3.2 복합·다중 이슈(Multi-Part Issue) 분할 판정 설계 (`verdict::judge_by_criteria` 확장)

기존 `docs/automation-mode.md` 9절의 실험 결과에서 증명되었듯, **여러 요건이 섞인 복합 상황을 한 질문으로 뭉뚱그려 물으면 모델이 위반 신호 하나를 놓치지만(방식 A: 39%), 기준별로 따로 쪼개어 묻고 최솟값을 취하면(방식 C: 78%, 함정 통과 0건) 정확도와 안전성이 극대화**됩니다.

이를 발전소의 복합·다중 이슈(`MULTI_ISSUE_CRITERIA`)에 그대로 적용합니다:

```rust
/// 발전소 복합·다중 이슈 심사를 위한 4대 직교 분할 기준 (verdict.rs 확장)
pub const PLANT_MULTI_CRITERIA: [&str; 4] = [
    "단일 계측기 오류(드리프트·노이즈)가 아닌 실제 물리적 계통 변화 여부",
    "상류 설비(Depth -1~-2)와 하류 설비 간 시계열 전파 시차(Δt) 및 물리량 보존 부합 여부",
    "우회 밸브 개방 또는 예비기 투입을 위한 선행 안전 절차(인터록·LOTO) 충족 여부",
    "설비 변경관리(MOC) 승인 한도 및 운전 기준치 이내 복구 가능 여부",
];

```

* **복합 이슈에서의 작동 방식**:
예를 들어 **`[103동 급수밸브 고착(설비 이슈)] + [현장 Red-line 도면 제출(절차 이슈)] + [101동 보일러 온도 상승(연쇄 파급 이슈)]`** 3가지가 동시에 얽힌 복합 사건이 들어오면:
1. 규칙 엔진이 각 부분 이슈의 통과 여부를 개별 플래그(`sensor_ok`, `upstream_causal`, `procedure_ok`, `moc_ok`)로 먼저 산출합니다.
2. 어느 한 부분이라도 불리한(`Adverse`) 이슈나 미완료 절차(`Procedural`)가 섞여 있으면 **절대 자동 확정하지 않고**, 주제어실 화면에 "이 사건은 [설비 상류 파급] + [절차 미완료] 2가지 이슈가 결합된 건입니다"라고 분해해서 보여줍니다.

3. 모든 부분 이슈가 안전 완화 조건(`Favorable`)을 충족했을 때만 `Zoro-1`에게 위 4가지 기준을 각각 따로 물어(`judge_by_criteria`), **4개 확률의 최솟값이 `0.95` 이상일 때만 자율 복구 제어를 확정**합니다.

### 5. 기존 `zoro-gravity` 코드 자산과의 정합성 요약

이 개선 기획(Part 8-6)이 강력한 이유는 **새로운 추상적 개념을 만든 것이 아니라, 이미 검증(L1~L4 통과)된 `zoro-gravity`의 핵심 설계 철학 3가지를 발전소 이슈 구조에 그대로 이식**했기 때문입니다:

1. **단일 이슈(Single Issue)**: `extract.rs`의 대장 기반 오독 교정과 `gate2_consistency.rs`의 원장 우선 원칙(단일 입력 오류 걸러내기)이 그대로 처리합니다.

2. **절차 이슈(Procedural Issue)**: `policy.rs`의 **불변식 2(절차 처분은 자동 확정 금지)**, **불변식 6(고위험 무입증 승인 `G3InterceptRubberStamp` 차단)**, 불변식 7(누락 서류 강제 진입 `G1InterceptForceHold` 차단)이 발전소의 안전 작업 절차(LOTO·MOC·인터록 순서) 위반을 100% 결정론적으로 막아냅니다.

3. **복합·다중 이슈(Multi-Part Issue)**: `graph.rs`의 홉 탐색이 공간·시간적으로 흩어진 연쇄 알람들을 하나의 뿌리(Root Cause)로 묶어주고, `verdict::judge_by_criteria`(방식 C)가 **설비·시차·센서·절차 기준을 하나씩 쪼개어 질문**함으로써 복합 상황에서 모델이 함정 하나를 놓쳐 오판하는 사고를 원천 차단합니다.
